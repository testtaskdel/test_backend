# CRM night sync

Синхронизация покупателей и сделок amoCRM в PostgreSQL. Точка входа —
`collect_leads_customers(is_full=True)`. JSON-формат `general` / `api_value`
и поля `amo_customers`, `amo_leads`, `amo_contacts`, `amo_companies` сохранены.

## Решения

- Вместо запроса и `commit` на каждую сущность используются пачки по 500 записей.
- `crm_entity_index` хранит уникальные CRM ID и индексируется по точным логину
  и названию. Это заменяет повторный поиск внутри JSONB-массивов и поддерживает
  поиск покупателя или сделки другими частями системы.
- Покупатель ищется по CRM ID, затем по логину среди сделок; сделка — по CRM ID,
  затем по логину среди покупателей. Неоднозначный логин не считается совпадением.
- Если ID сделки и логин покупателя указывают на разные группы, данные переносятся
  в группу сделки, а вторая группа удаляется. Связь сделки с покупателем остаётся
  внутри одной общей записи.
- Очистка начинается только после полного чтения обоих потоков. Она удаляет
  отсутствующие записи и элементы с «удалить» в имени. Родительская таблица
  обходится keyset-пачками, без загрузки всей таблицы в память.
- Ошибки не проглатываются. Уже записанные пачки сохраняются, но при прерывании
  выгрузки очистка не запускается. Статус запуска записывается в `crm_sync_run`.
- Убраны не описанные в задании фильтры по жёстко заданным ID статусов.

## Запуск

Python 3.9+, PostgreSQL 12+:

```bash
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\\Scripts\\activate
pip install -r requirements.txt
cp .env.example .env
flask --app wsgi:app init-db
```

Для существующей базы один раз восстановите индекс из старых JSONB-данных:

```bash
flask --app wsgi:app rebuild-entity-index
```

Клиент amoCRM не добавлен: его нет в исходном задании, и боевой API поднимать
не требуется. Передайте источник через `CrmSource` или `CallableCrmSource`:

```python
from crm_sync import create_app
from crm_sync.sync import CallableCrmSource, collect_leads_customers

source = CallableCrmSource(customers_factory=get_customers, leads_factory=get_leads)
app = create_app({"CRM_SOURCE": source})
with app.app_context():
    result = collect_leads_customers(is_full=True)
```

Источник должен выдавать потоковые словари amoCRM (`id`, `name`,
`custom_fields_values`, `_embedded`) или совместимые объекты. Для частичного
прохода используйте `is_full=False` — в этом режиме очистки нет. Секреты CRM
передавайте через переменные окружения, не храните их в коде.

## Оценка нагрузки

Для 20 тыс. покупателей и 50 тыс. сделок при размере пачки 500 получается
140 пачек. На пачку выполняется до двух выборок (индексы и родительские строки),
то есть до ~280 основных SELECT, плюс пакетные записи и 140 фиксаций транзакций.
Это оценка числа выборок, а не всех SQL write-операций. Полная очистка добавляет
keyset-страницы по группам и индексам.

В памяти хранятся ID полного снимка и одна пачка, а не ORM-объекты всей таблицы.
Для 70 тыс. целочисленных ID обычно нужны несколько мегабайт; вместе с пачкой и
кэшем разумно закладывать десятки мегабайт. Пик зависит от размера `api_value`,
числа вложенных контактов/компаний и крупных JSONB-массивов. Это оценка, не замер.

## Проверки

```bash
pip install -e '.[test]'
python -m pytest
```

Тесты используют SQLite для бизнес-логики; рабочая схема рассчитана на PostgreSQL.
Существующие данные остаются в `abstract_customer`, но перед первым запуском
нового кода нужно выполнить `rebuild-entity-index`. Предполагается один
одновременный запуск синхронизации.
